## ค่าที่ eVRP ยืนยันและนำมาใช้

| เรื่อง | ค่า |
|---|---|
| `pickup_hub_code` | `TS-h01` (ใช้ได้ทั้งนครปฐมและกรุงเทพ จึงตั้งเป็นค่าคงที่) |
| `delivery_point_code` | เท่ากับรหัสลูกค้า — eVRP สร้างจุดส่งด้วยรหัสเดียวกับลูกค้า |
| `delivery_date` | `order_date + 1 วัน` ถ้าตรงวันอาทิตย์เลื่อนเป็นวันจันทร์ |
| Customer master | ตั้งให้แล้ว 7 จาก 8 ราย |

query ใช้ `DATEDIFF(day, '19000107', ...) % 7 = 0` เพื่อตรวจวันอาทิตย์ จึงไม่ขึ้นกับ `DATEFIRST`
หรือภาษาของ SQL Server

## ปัญหาที่พบระหว่างทางและวิธีแก้

| ปัญหา | ผลถ้าไม่แก้ | วิธีแก้ |
|---|---|---|
| `TRY_CONVERT(float, '')` คืน `0` และ eVRP อ่าน `0` ว่า COD | คนขับไปเก็บเงินปลายทางผิดใบ (พบ 1 ใบ) | `NULLIF(LTRIM(RTRIM(...)), '')` ก่อนแปลง + ทดสอบในโค้ด |
| `description` ว่างได้ในสัญญาเดิมของเรา แต่ eVRP บังคับ | ทั้ง batch ถูกปฏิเสธ | fallback `ItemName` → `Description` → `ItemCode` และบังคับใน `contracts.py` |
| `TOP (n)` จำกัดจำนวน **แถว** ไม่ใช่จำนวนใบ | ใบที่เกินโควตาไม่ถูกส่งเลยแม้รอบถัดไป | ขยายเป็น 5000 หลังนับพบ 293 แถว/วัน |
| eVRP จอง `request_id` แม้ปฏิเสธ payload | แก้ข้อมูลแล้วส่งใหม่ไม่ได้ (409) | `request_id` = hash(order_no) + hash(เนื้อข้อมูล) |
| รหัสคลังของ ERP ไม่ใช่รหัส hub ของ eVRP | 422 ทุกใบ | ใช้ `TS-h01` ตามที่ eVRP ยืนยัน |

## ขั้นตอนเมื่อ eVRP ตั้ง master ของ CJ Express เสร็จ

ปลด claim เฉพาะ 2 ใบนี้ แล้วรอบถัดไประบบจะส่งเอง:

```sh
docker compose -f deploy/docker-compose.yml exec -T thaisausage python -c "
import sqlite3
db = sqlite3.connect('data/integration.sqlite3')
with db:
    for so in ('SO-L2609-1851', 'SO-L2609-1872'):
        db.execute('DELETE FROM order_claims WHERE TRIM(order_no)=?', (so,))
    db.execute(\"DELETE FROM submissions WHERE state='needs_review'\")
print('ปลดแล้ว รอรอบถัดไป')"
```

ทำได้เพราะ `422` คือการปฏิเสธที่ชัดเจน ไม่มีข้อมูลค้างฝั่ง eVRP — ห้ามใช้วิธีนี้กับ `needs_review`
ที่เกิดจาก timeout ซึ่งผลลัพธ์ไม่แน่นอน
