## Sequence of real attempts

1. First live send → `422` with no detail stored. Added upstream error capture.
2. Corrected hub code, resent under the same identity → `409 REQUEST_ID_CONFLICT`: eVRP keeps a
   request_id even for a payload it refused. Fixed by deriving the identity from the order content.
3. Resent with a new identity → `422` listing two field errors:
   - `pickup_hub_code` / `PICKUP_HUB_NOT_FOUND` — `h01` from the vendor sample is absent from the
     production Master Hub.
   - `customer.code` / `CUSTOMER_MASTER_REQUIRED` — the customer needs a master record, a delivery
     point and a route inside eVRP before any SO referencing it is accepted.
   - warning `DELIVERY_DATE_DEFAULTED` — an empty `delivery_date` falls back to `order_date`.

Every other mapped field passed eVRP validation.

## Fixes made during go-live

- Upstream refusal text is stored with the submission (`upstream_error`, 2000 characters).
- Scheduled `request_id` combines order number and payload hash.
- `TOP` in the approved query limits rows, not orders; raised from 50 to 5000 after the row count
  showed 21 of 108 orders were reachable per cycle.
- SQL credentials split out of the connection string; `.env` on the VPS had them embedded.

## Safety position

No ERP row was created or modified: the DO writer stays disabled and the SQL account is used for
SELECT only. Each order reaches eVRP at most once because `order_claims` is written before the
outbound call, so the failed attempts above produced one request each, not a retry loop.
