## TransactionNo

ทีม ERP ยืนยันว่าแอปของเขาออกเลขด้วย `SELECT MAX + 1` เหมือนกัน ซึ่งตรงกับที่ implement ไว้ และของเรา
เพิ่ม `WITH (UPDLOCK, HOLDLOCK)` ให้ล็อกค้างจนจบ transaction

ความเสี่ยงที่เหลือ: PK คือ `(RowOrder, TransactionNo)` ที่ `RowOrder` เป็น identity ดังนั้น**ถ้าเลข
ซ้ำ ฐานข้อมูลจะไม่ฟ้อง** จะได้เอกสารสองใบเลขเดียวกันเงียบๆ ถ้าแอป ERP อ่าน `MAX` แบบไม่มี `UPDLOCK`
ก็ยังมีช่องเล็กๆ ที่ชนกันได้ — เป็นช่องเดียวกับที่แอปเขามีอยู่แล้วระหว่างผู้ใช้สองคน ไม่ใช่ช่องใหม่
ทางปิดสนิทคือขอให้ ERP กันช่วงเลขให้ DO จาก eVRP โดยเฉพาะ (เช่น 900000+) ยังไม่ได้ทำ

## เครื่องมือที่เพิ่มระหว่างทาง

- `python -m thaisausage.verify_do --transaction-no N [--receipt-id ID]` — อ่านเอกสารกลับจาก ERP
  แล้วเทียบกับที่ส่งไปทีละคอลัมน์ อ่านอย่างเดียว รันได้ตลอด
- `python -m thaisausage.status --days N` — สรุปว่าส่ง SO ไปเท่าไร ค้างอะไร DO เข้ามากี่ใบ
  อะไรต้องให้คนดู อ่านจากฐานเราอย่างเดียว
- `python3 deploy/assemble_config.py [--check]` — ประกอบ/ตรวจ config จากสองไฟล์ที่อยู่ใน git

## บั๊กที่เจอและแก้ระหว่างทาง

1. `--transaction-no` ยังบังคับใส่ ทั้งที่ระบบออกเลขเองได้ → ซ้อมเขียนตามคู่มือจะ error (`1f07df0`)
2. ตัวอย่าง JSON ในสัญญาบอก `item_code` แต่ mapping บอก `itemcode` → ใบที่ทำตามตัวอย่างถูกปฏิเสธ
   ถ้าไม่เจอตอนนี้ eVRP จะไปเจอเองตอนพัฒนา (`6da3442`)
3. callback ข้ามการเขียนทุกครั้งที่ไม่ได้รับ `TransactionNo` — ซึ่งคือทุกครั้ง เพราะ eVRP ไม่ต้องส่ง
   มา แปลว่าต่อให้เปิด `enabled` ก็จะไม่มีวันเขียน (`6da3442`)
